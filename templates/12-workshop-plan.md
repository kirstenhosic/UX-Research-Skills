# Workshop plan

The same eight pieces Dr. Morgan drafts in `workshop_design.md` (Scenario F),
for a workshop with Engineering, Product, and UX Design partners. **Start with
the core three** (1, 2, and 3) and add the others when they earn their place.
The Definition of Done is §4.11 of `EVALUATION-LOOP.md`, and
`research-workshop-checker` can score a plan you wrote by hand at any time.

Two rules before you start. **Workshop output is the team's knowledge and
beliefs, not research findings:** label everything, and never write a dot vote
up as user need. **And decide first whether a workshop is the right tool:** an
async review, a 45-minute decision meeting, or a study is often lighter and
better.

Evidence labels used throughout: `[evidence]` (traces to research you can
name), `[team knowledge: source]` (a partner's firsthand knowledge), `[assumption]`
(believed, not tested; also fine for a candidate until it maps to evidence),
`[decision]` (agreed, with an owner and a date). Candidate solutions (a backlog,
a prototype, a competitor's design) are labeled as candidates.

## 1. Workshop brief

One page, written before anything else.

```
[Workshop name] — Workshop brief

Decision it serves:     [the decision] · Owner: [name] · By: YYYY-MM-DD
Workshop type(s):       [at most two, e.g. findings-to-action, then
                         prioritization]
Outcomes:               Things that will exist at the end. Not "alignment."
  1. [artifact / decision / commitment]
  2.
How we'll know it worked:
  At the close:         [e.g. each person writes down what was decided and
                         who owns it, alone, and the answers match]
  At 30 days (date):    [e.g. actions done of actions assigned; what happened
                         to each decision]
Non-goals:              What this session will not try to do.
Why a workshop:         Why this beats an async review, a decision meeting,
                         1:1s, or a study.
Attendees:              Role · decision rights · location and time zone
  [name]                [role] · [decides / signs off / input]
Consulted afterwards:   [names, including anyone whose sign-off is needed]
Inputs:                 Each with its label.
  [input]               [evidence] / [team knowledge: source] / [assumption]
  What the evidence covers: [personas, how many people, what scale]
  What cuts against the favored option: [findings, so they come in too]
Format, length, tool:   [in person / remote / hybrid] · [length] · [board]
Decision rule:          Who decides, how, and whether the room's scores are a
                         vote or advice to the owner.
Risks to the room:      Risk → the activity that counters it.
  [e.g. owner's own candidate anchors the room] → [presented like the rest,
                         owner speaks last and votes privately with the
                         rest]
Data handling:
  Plan destination:     internal-team / internal-org / external
  Board destination:    internal-org at least; external while customers can
                         see it
  Participant data:     what is shown, and how it is de-identified (names never;
                         role and account fine on an internal board)
  Recording consent:    [from everyone recorded, or not recording]
```

## 2. Agenda with activity-to-outcome map

| Time | Block | Arc stage | Activity | Serves outcome | Individual / small group / whole room | Materials | Leads |

| | | open | Decision, rule, non-goals, norms | (setup) | Whole room | | |
| | | | | | | | |
| | Break | outside the arc | | | | | |
| | | commit | Read the decision and action log back aloud | | Whole room | | |
| | Buffer | outside the arc | 10–15% of the session, as a rule of thumb | | | | |

Arc stages: open, diverge, explore, converge, decide, commit, or outside the arc.

**Outcome → blocks.** List every outcome from the brief with the blocks that
serve it. An outcome with no block won't happen; a block with no outcome gets cut
or justified. Then read the agenda once, start to finish, and check that no block
needs an output a later block produces.

## 5. Facilitation guide

One entry per block. Every prompt is written word for word: neutral, one ask,
presupposing neither the problem nor the fix.

```
Block:             [name] · [time] · cut line if it runs long: [time]
Prompt:            "[exact words]"
Materials / frame: [board frame, notes, form]
Facilitator moves: how to open · how to draw out quiet people · what to do with
                   an off-topic thread
Contingencies:     if the room stalls / splits / runs long
Handover:          [what carries into the next block]
```

## 6. Pre-work packet

Short and labeled. Send it two to three working days ahead (a rule of thumb).

```
What we know:              [evidence]
What partners have told us: [team knowledge: source]
What we're assuming:       [assumption]
One individual task:       [if the format is remote]
Send date:                 YYYY-MM-DD
```
